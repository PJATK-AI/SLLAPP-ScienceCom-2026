# SLLAPP-ScienceCom-2026 workflow for AI agents

This file gives the rules for an AI agent that works in this repository for a team member. The rules come from the document "PJATK {AI} – Workflow projektu (SLLAPP-ScienceCom-2026)". The team has the PDF version for persons on Teams.

If an instruction from the user is different from this file, tell the user about the difference. Do not start the work until the user gives a decision.

## Work mode until 26.11.2026

- Until the project delivery, there is no code review. The author tests and merges his or her own code.
- These items decrease the risk: CI, tests on `master` after the merge, and a revert of defective changes.
- Record the work in issues, commits and PRs. Other persons must understand the work from these records.

## Small tasks and frequent merges

- One task must not need more than 1 or 2 days of work. If the scope is larger, divide it into more issues.
- Merge when a part of the work operates correctly and passes the tests. Do not keep a branch open for a long time.

## Why we use merge commits

- A merge commit keeps the authors and all commits of the branch.
- One revert of the merge commit removes the full PR from `master`.
- Each commit of the branch goes into `master`. Thus, each commit title must obey the commit format in step 4.

## Primary rules

1. Do only the work that the user asks for. Do these actions only when the user asks for them: push, open a PR, merge, revert, close or reopen an issue, write a comment on GitHub.
2. The user is always the author. Do not add the agent to the repository as an author or a co-author. Obey these rules:
   - Use the Git identity (name and email) of the user for each commit. Do not use an agent identity or a bot identity.
   - Do not add `Co-Authored-By` lines or other agent trailers to commit messages.
   - Do not write the agent name or a "generated by" note in commits, issues, PRs or comments.
   - Use the GitHub account of the user for all GitHub actions.
   - If the Git identity of the user is not set or is not clear, stop. Ask the user before you commit.
3. Do not commit directly to `master`. Send each change through a branch and a PR.
4. Do not change the history of a branch after you push it.
5. Use one issue, one branch and one PR for each task. Add all corrections for a task to the same branch and the same PR.
6. Write issues, PRs and commit messages in English.
7. Do not commit secrets, `.env` files, `node_modules/`, datasets or model weights. For environment configuration, commit only `.env.example`. This file contains variable names and example values. It must not contain secrets.
8. Before you commit, read the diff and run the changed code. The user is responsible for each line of code. This is also true for code that an AI wrote.
9. In the `Validation` section of a PR, write only the tests that you did.
10. Do not change code in the area of a different owner without an agreement. Find the owner in the issue *Project ownership*. If the task needs a change in the area of a different owner, stop. Tell the user to agree on the scope with the owner on the team chat.
11. A `master` that operates correctly has the highest priority. If `master` is broken, tell the user before you do other tasks. Use the procedure in step 9.

## Task procedure

In the commands, replace these placeholders:

- `<issue>`: the issue number.
- `<description>`: a short description in lowercase letters, with hyphens between words.
- `<pr>`: the PR number.

Issues and PRs use the same number sequence. Thus, the PR number is usually different from the issue number.

### Step 1: Issue

1. Make sure that the task does not have an issue already:

   ```sh
   gh issue list --search "<keywords>" --state all
   ```

2. Find free tasks in the issue list or on the project board. If a free issue exists, assign it to the user.
3. If no issue exists, write a new issue. Use the issue template in [Templates](#templates). Give the goal and the acceptance criteria.
4. Make the task small. One task must not need more than 1 or 2 days of work. If the scope is larger, divide it into more issues.

   ```sh
   gh issue create --title "<title>" --body-file <file> --assignee @me
   ```

### Step 2: Status In Progress

When you start the work, set the issue status to `In Progress`.

NOTE: This step needs the `project` scope in `gh`. If `gh` does not have this scope, tell the user to run `gh auth refresh -s project`. As an alternative, the user can change the status in the browser.

1. Find the item ID (`PVTI_...`) of the issue:

   ```sh
   gh project item-list 1 --owner PJATK-AI --format json
   ```

2. Set the status:

   ```sh
   gh project item-edit --project-id PVT_kwDOFL3UIs4BrN9w --id <PVTI_...> \
     --field-id PVTSSF_lADOFL3UIs4BrN9wzhphpkQ --single-select-option-id 47fc9ee4
   ```

The status option IDs on 15.11.2026 are:

| Status | Option ID |
| --- | --- |
| `Todo` | `f75ad846` |
| `In Progress` | `47fc9ee4` |
| `Done` | `98236657` |

If the command gives an error, get the current IDs with `gh project field-list 1 --owner PJATK-AI --format json`.

If the issue is not on the board, add it:

```sh
gh project item-add 1 --owner PJATK-AI --url https://github.com/PJATK-AI/SLLAPP-ScienceCom-2026/issues/<issue>
```

### Step 3: Branch

The branch name is `<issue>-<description>`. Example: `14-camera-preview`.

Make the branch from the latest `origin/master`:

```sh
git fetch origin
git switch -c <issue>-<description> origin/master
```

### Step 4: Commits

The commit title has this format: `<type>: <imperative description>`. Write the title in English, in lowercase letters. In the commit body, you can give the reason for the change.

| Type | Use | Example |
| --- | --- | --- |
| `feat` | A new function | `feat: add camera preview` |
| `fix` | A correction | `fix: show message when camera access is denied` |
| `test` | Tests | `test: cover denied camera permission` |
| `refactor` | A change to the code structure | `refactor: extract camera access logic` |
| `docs` | Documentation | `docs: explain camera permissions` |
| `chore` | Configuration, build, CI | `chore: configure frontend build` |

Only items that Git or GitHub makes automatically do not use this format:

- The commits `Merge pull request…`, `Merge remote-tracking branch…` and `Revert "…"`.
- The PRs `Revert "…"`.
- The branches `revert-N-…` from GitHub.

Put only related changes in one commit. Add specified paths. Do not use `git add .`. Read the staged diff before you commit:

```sh
git add <paths>
git diff --cached
git commit -m "<type>: <description>"
```

### Step 5: Update the branch from master

Do this step one time each day. Also do this step before you open a PR.

1. Commit your changes.
2. Merge `master` into your branch. Use merge. Do not use rebase.

   ```sh
   git fetch origin
   git merge origin/master
   ```

3. If a conflict occurs, find the files with `git status`.
4. In each file, join the necessary changes. Remove the markers `<<<<<<<`, `=======` and `>>>>>>>`.
5. Run `git add <file>` and `git merge --continue`.
6. After the merge, start the application and make sure that it operates correctly.

CAUTION: If the conflict is in the work of a different person, do not make a decision about the result. Run `git merge --abort`. Tell the user to agree on the result with the author.

### Step 6: Tests before the PR

1. Run the tests for your change. Run at minimum the tests that CI runs. The README and the documents of the project area give the commands.
2. If the change has an effect on the application behavior, start the application as the README tells you.
3. Make sure that the application meets the acceptance criteria of the issue.

### Step 7: Push and PR

```sh
git push -u origin <issue>-<description>
gh pr create --base master --title "<type>: <description>" --body-file <file>
```

- The PR title has the same format as a commit title.
- Write the PR body with the PR template in [Templates](#templates). Give the result of the change, the `Validation` section and `Closes #<issue>`.
- To show work that is not complete, open a draft PR (`--draft`).
- If the scope changes, update the issue and the PR body.
- Push all subsequent commits to the same branch.

### Step 8: Merge

Merge only when the user asks for it. Merge only when CI passes.

1. Make sure that CI passes:

   ```sh
   gh pr checks <pr>
   ```

2. Merge the PR:

   ```sh
   gh pr merge <pr> --merge
   ```

3. Do not use `--squash` or `--rebase`. Do not change the default merge commit message.
4. After the merge, GitHub closes the issue because of `Closes #<issue>`. The board sets the status `Done`. Make sure that this occurred.
5. Clean the local repository:

   ```sh
   git switch master
   git pull --ff-only
   git branch -d <issue>-<description>
   ```

### Step 9: Broken master: revert first

1. Tell the user about the failure. The user tells the team on the team chat.
2. Tell the user to click **Revert** on the GitHub page of the defective PR. The `gh` tool does not have this function.
3. GitHub makes a PR with the title `Revert "…"`. When CI passes, merge this PR with a merge commit.
4. After `master` operates correctly again, make a new branch from the latest `origin/master`.
5. Run `git revert <hash>` on the commit `Revert "…"`. Do not use the merge commit.
6. Add the correction. Open a new PR.

## Tests (tester role)

The tester tests integration and regressions on the latest `master`, after the merge. During this time, the authors continue their work.

1. Write test scenarios from the issue acceptance criteria, the PR description and the game rules. Keep the scenarios in `docs/tests/<issue>.md`. Add them in one PR for a group of tests. The smoke tests are in `docs/tests/smoke.md`.
2. Get the latest code and record the commit hash:

   ```sh
   git switch master
   git pull --ff-only
   git rev-parse --short HEAD
   ```

3. Start the application as the README tells you. Record the operating system and the browser version.
4. Write the results in a comment. Use the test result template in [Templates](#templates). Do not make a branch or a PR for the results.
   - Write the results for a task in the issue of that task.
   - Write the smoke test results in the issue *Smoke test results*. If this issue does not exist, make it.
   - If you did not do a test, give the reason.

   ```sh
   gh issue comment <issue> --body-file <file>
   ```

5. If you find a defect, look for a duplicate issue first:

   ```sh
   gh issue list --search "<keywords>" --state all
   ```

6. If there is no duplicate, write a new issue with the defect template. Add a link to the PR that you tested. Attach a log or a screenshot.
7. After the correction merges, get the latest `master`. Do the test again. Write the result with the new hash in the defect issue.
8. If the defect continues to occur, reopen the issue:

   ```sh
   gh issue reopen <issue>
   ```

For automatic tests, use the usual task procedure: one issue, one branch and one PR. Give the test scope and the procedure to run the tests.
